# Design: Live updates reach the browser

## Approach

Three changes, each small:

1. **A switch.** `config.enable_live_updates` (default `false`) is checked first in
   `Services::ErrorBroadcaster.available?`. That method is already the one gate for both ends: the
   `ErrorLog` commit callbacks reach it through `broadcast_new`, `broadcast_update` and
   `broadcast_stats`, and the index view's guard calls it. Turning the switch off therefore stops
   every broadcast, every stream tag and the "Live" badge at once.
2. **A client.** When the index renders its stream tags, it also fills a new `content_for(:red_head)`
   slot, which the layout yields inside `<head>`. That slot holds two things:
   - `action_cable_meta_tag`, so a host's custom cable URL or mount path is honoured;
   - one `<script type="module">` for `@hotwired/turbo-rails@8.0.23` `turbo.js`, pinned by version
     and SHA-384, with `crossorigin="anonymous"` and the host's CSP nonce.

   One helper builds both, and one helper replaces the three-part guard that is repeated in the
   view today.
3. **Page scripts that survive Turbo.**
   - The tooltip and local-time initialisers become idempotent per element: they skip elements they
     have already set up, and tooltips use `bootstrap.Tooltip.getOrCreateInstance`.
   - The local-time initialisers also run on elements that a stream render inserts.
   - `<body data-turbo="false">` stays, so Drive never takes over navigation.

Lab evidence for this approach (Lab A, 2026-10-22):

- The client alone makes rows arrive.
- It also makes `turbo:load` re-run `convertToLocalTime`, which stacks a second click listener and
  cancels the toggle.
- A streamed row's `local_time_ago` keeps the server's `time_ago_in_words` text, in the host app's
  I18n locale, and its click-to-toggle is never wired.

## Decision: Gate inside `ErrorBroadcaster.available?`   (→ REQ-1, REQ-2, REQ-3)

**Context.** The setting must stop:
- the capture-path work (row partials, column-visibility queries, the throttled `DashboardStats`);
- the view's stream tags;
- the badge.

Today the server and the view agree because both ask `available?`.

**Alternatives.**
1. Check the setting first inside `available?`.
2. Make the `ErrorLog` callbacks conditional (`after_create_commit ..., if: -> { enabled }`), and
   add a separate check in the view.
3. Both.

**Case for 1.** One gate, so the two ends cannot disagree. The view and the broadcaster already
share it, and its circuit breaker (#114) is untouched. With the setting off, `available?` returns
before touching ActionCable.

**Case against 1.** The callbacks still fire and make one method call each, so a capture is not
quite zero-cost. `available?` now mixes a config question with an infrastructure one.

**Decision.** We chose 1.
**Falsifiability.** We would move the gate onto the callbacks if the overhead benchmark (product
goal 2) shows the switched-off callbacks cost more than 0.05 ms per capture.
**Fired-if.** manual

## Decision: Load the client from jsDelivr, the unminified npm file, with SRI   (→ REQ-4)

**Context.**
- The layout may not use the asset pipeline or `public/`. External JS comes from a CDN (CLAUDE.md
  rules 3, 5, 6).
- The client must define `turbo-cable-stream-source` and carry an ActionCable consumer. Plain
  `@hotwired/turbo` (the 2025 import) does neither.
- `@hotwired/turbo-rails` ships only an unminified ESM bundle, `app/assets/javascripts/turbo.js`.
  It is self-contained: 8.0.23 is byte-identical to the turbo-rails 2.0.23 gem's file. It is 189 KB
  raw and 41 KB brotli.

**Alternatives.**
1. jsDelivr, the npm `turbo.js` at a pinned version, with `integrity`.
2. jsDelivr's auto-minified `turbo.min.js`, with `integrity`.
3. Serve the host's own turbo-rails gem file through an engine route. The version always matches
   the host's server gem, and there is no CDN.
4. jsDelivr's `+esm` endpoint.

**Case for 1.** It follows the layout's existing convention. The bytes are the published package
file, so the hash cannot drift while the URL stays the same. A wrong hash blocks the script, and
the system spec sees that, because it serves the vendored copy under the same integrity check.

**Case against 1.**
- It is a 41 KB download on the index. That is only the index, and only when the feature is on.
- One client version is used for every host's turbo-rails. This relies on the
  `Turbo::StreamsChannel` subscribe protocol and the `prepend`/`replace` actions staying
  compatible, which they have been since turbo-rails 1.0.
- A CDN outage silently turns live updates off. The page still works.
- Options 2 and 4 are generated by jsDelivr, so their bytes can change and break an SRI hash, which
  would kill the feature unnoticed again: the F1 pattern.
- Option 3 adds a route that reads another gem's internal file layout.

**Decision.** We chose 1.
**Falsifiability.** We would switch to option 3 if a turbo-rails version that RED supports breaks
the pinned client, that is, if a CI row on that version fails the live-updates system spec.
**Fired-if.** manual

## Decision: Tags go in `<head>` through `content_for(:red_head)`, from the index only   (→ REQ-6, REQ-9)

**Context.** ActionCable's `getConfig` reads `document.head` for `meta[name='action-cable-url']`, so
that meta tag must be in `<head>`. Only `errors/index.html.erb` subscribes to streams.

**Alternatives.**
1. The layout always loads the client and the meta tag.
2. The index emits both in its body.
3. The index fills `content_for(:red_head)`, which the layout yields in `<head>`.

**Case for 3.** Pages that don't subscribe load nothing new, and the meta tag sits where ActionCable
looks for it. One helper emits both, so a page cannot load one without the other.

**Case against 3.** It adds one more yield to a 2,600-line layout. A future page that subscribes has
to remember to call the helper.

**Decision.** We chose 3.
**Falsifiability.** We would move to automatic layout-level loading (whenever a page sets
`@live_streams`) once a second view subscribes to streams.
**Fired-if.** `test "$(grep -rl 'turbo_stream_from' app/views | wc -l)" -gt 1`

## Decision: Idempotent per-element initialisers, re-run after stream renders   (→ REQ-7, REQ-8, REQ-13)

**Context.**
- The layout registers its tooltip and local-time initialisers on `DOMContentLoaded`, and again on
  `turbo:load` / `turbo:frame-load` when `Turbo` is defined. Turbo fires `turbo:load` on the first
  page load as well, so loading the client runs them twice. The lab showed the cancelled
  local-time toggle.
- Rows inserted by a stream never get initialised at all.
- The dashboard has no Turbo frames, and Drive is off.

**Alternatives.**
1. Delete the `turbo:load` / `turbo:frame-load` listeners. They can only duplicate
   `DOMContentLoaded` while Drive is off.
2. Make each initialiser skip elements it has already set up, and also run the local-time ones on
   content a stream inserts.
3. Option 1 plus a stream hook.

**Case for 2.** One mechanism fixes the double run, the un-initialised streamed rows and any future
re-render. It doesn't depend on which events Turbo happens to fire.

**Case against 2.** It means more edits inside the layout's script blocks, plus a marker data
attribute on each element. The `turbo:load` listeners stay as harmless no-ops, which a later reader
may find puzzling. A comment will say why.

**Decision.** We chose 2.
**Falsifiability.** We would revisit this if the dashboard turns on Turbo Drive or adds Turbo
frames, because then whole-page renders replace elements and the event model changes.
**Fired-if.** `grep -rqE 'turbo_frame_tag|data-turbo="true"' app/views`

## Decision: Off by default   (→ REQ-1)

**Context.** Product non-goal (paramount): every request-path feature must be switchable. The
feature has delivered nothing since v0.1.4, but it has cost every capture a render on hosts with
Turbo and ActionCable loaded.

**Alternatives.**
1. Default `false`.
2. Default `true`.
3. No switch.

**Case for 1.**
- No user loses visible behaviour.
- The capture path of every host stops doing work for nobody.
- It matches the other opt-in features that have a cost (breadcrumbs, local variables).
- The setting lands before 1.0 freezes the config.

**Case against 1.** Discoverability. A host that already has ActionCable and expects live updates
gets nothing until it opts in, and the docs' "out of the box" line has to go.

**Decision.** We chose 1 (the user, 2026-10-22).
**Falsifiability.** We would reconsider defaulting to on if three or more issues or discussions
within three months of the release ask why live updates are off by default.
**Fired-if.** manual

## Decision: Prove the browser half with a Cuprite system spec   (→ REQ-5, REQ-7, REQ-8)

**Context.**
- `live_stream_delivery_spec` already proves server-side delivery, through a real async adapter.
- No layer ever loaded the page in a browser and waited for a row. That is how F1 survived ten
  months.
- The dummy app loads ActionCable (`rails/all`) and turbo-rails (`Gemfile`), but has no
  `cable.yml`.

**Alternatives.**
1. A system spec:
   - Cuprite, with the async adapter installed at runtime the way the delivery spec does it;
   - the vendored `turbo.js` served for the CDN URL by the existing interceptor, with
     `Access-Control-Allow-Origin`, because module scripts fetch in CORS mode;
   - a non-transactional example, because `after_create_commit` must fire and the Puma thread
     must see the row.
2. A chaos phase. The harness speaks only HTTP and has no browser.
3. Request specs only. These cannot see whether a browser connects.

**Case for 1.** It is the missing layer, built from parts the suite already has (the interceptor,
the vendored files, Cuprite). A stale integrity hash also turns it red, because the browser enforces
SRI on the served bytes. A unit example also asserts that the SHA-384 of the vendored file equals
the pinned hash.

**Case against 1.**
- The async adapter is in-process, so cross-process delivery (solid_cable, redis) stays unproven.
  That part belongs to the host's adapter.
- It adds a 189 KB vendored file to the repository. The gem doesn't ship it; `spec.files` excludes
  `spec/`.

**Decision.** We chose 1.
**Falsifiability.** We would add a solid_cable chaos phase if a user reports rows not arriving on
a cross-process adapter while this spec is green.
**Fired-if.** manual

## Data / interface changes

- **Config (public, before the 1.0 freeze):** `enable_live_updates`, Boolean, default `false`
  (REQ-1).
- **Config warning (REQ-10):** in `validate!` (run in `after_initialize`), when the switch is on and
  `Turbo` or `ActionCable` is undefined. It warns and does not auto-disable, because `available?`
  already declines.
- **Layout:** a `yield :red_head` inside `<head>` (REQ-6, REQ-9).
- **Helpers:**
  - `red_live_updates?`, the guard used three times in the index today;
  - `red_live_updates_client_tags`, which emits the meta tag and the script;
  - pinned constants for the client URL and its integrity value (REQ-4).
- **Installer template:** an `enable_live_updates = false` block with the host requirements
  (REQ-11).
- **Specs:** examples that assert real broadcasts set `enable_live_updates = true`. The
  `rails_helper` reset restores the gem default (off) before each example.
- **Vendored test asset:** `spec/support/vendor/turbo.js`, listed in `VENDORED_SCRIPTS` and in the
  vendor README.
